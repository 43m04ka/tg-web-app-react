# AuraPay: что нужно знать фронту

Вторая касса **AuraPay** подключена **только для пополнения Steam**. Каталог (PS, Xbox и прочее)
остаётся на Paykeeper и не меняется вообще.

**Статус на 09.08.2026:** серверная часть готова целиком, касса сайта подключена и проверена
боевыми запросами, касса Telegram-бота ждёт ключей от AuraPay. Платежей ещё не проводили.

**Одно ломающее изменение — `platform` стал обязательным** при создании Steam-заказа (раздел 2).
Всё остальное обратно совместимо: новые поля только добавлены, ничего не удалено и не переименовано.

Порядок чтения: раздел 2 обязателен к правке на фронте, раздел 5 — задача для админки,
разделы 1, 3, 4 — про поведение, которое стоит учесть в интерфейсе.

---

## 1. Оплата Steam

Контракт `POST /api/steam/create` прежний:

```json
{
  "orderId": 1234,
  "status": "awaiting_payment",
  "topupAmount": 1000,
  "total": 1151,
  "paymentUrl": "https://payform.aurapay.tech/9131d8de-9e82-4b78-9642-ad034f9dfd17"
}
```

**Единственное отличие:** `paymentUrl` теперь ведёт на домен **`payform.aurapay.tech`**, а не на Paykeeper
(домен проверен боевым запросом к кассе). Если где-то есть проверка домена, whitelist iframe-источников
или вшитая ссылка на Paykeeper — её нужно снять.

Способ оплаты фиксирован — **СБП**. Выбора «карта/СБП» на странице кассы не будет:
комиссия зависит от способа, а итоговую сумму мы называем покупателю заранее.

Срок жизни ссылки прежний — `PAYMENT_LINK_TTL_MINUTES` (по умолчанию 15 минут).
По истечении заказ уходит в `payment_failed`.

Статус опрашивается как и раньше:

```
GET /api/payment/status?id={orderId}
→ { id, type, status, paymentMethod, total }
```

Оплата подтверждается двумя путями — вебхуком от кассы и фоновым поллингом раз в 15 секунд,
поэтому статус `paid` может появиться с задержкой в несколько секунд после возврата с оплаты.
Логика опроса на фронте не меняется.

## 2. ВАЖНО: `platform` теперь обязателен при создании Steam-заказа

Касс AuraPay **две**: своя у Telegram-бота и своя у сайта. Заказ уходит в кассу своей площадки —
на её баланс приходят деньги, и с неё же уходит пополнение Steam. Определяется это по полю
`platform` в теле `POST /api/steam/create`.

Поле существовало и раньше, но **не проверялось**: если фронт его не присылал, сервер молча
подставлял `web`. Теперь так нельзя — заказ из бота ушёл бы деньгами на кассу сайта.

**Присылать `platform` обязательно.** Без него или с неизвестным значением вернётся `400`:

```json
{ "error": "platform is required, one of: tg, web, vk, max" }
```

Допустимые значения и куда идут деньги:

| `platform` | Откуда заказ | Касса |
|-----------|--------------|-------|
| `tg` | Telegram-бот / Telegram Web App | касса бота |
| `web` | сайт в браузере | касса сайта |
| `vk` | VK-приложение | касса сайта |
| `max` | площадка MAX | касса сайта |

**Статус подключения касс на 09.08.2026:** касса сайта заведена и проверена, касса бота ждёт ключей.
Пока её не подключат, заказ с `platform: tg` получит `400` с текстом:

```json
{ "error": "Пополнение Steam с этой площадки временно недоступно. Напишите менеджеру." }
```

Этот текст можно показывать покупателю как есть. Со стороны сервера бот полностью готов —
подключение сведётся к добавлению ключей, релиз фронта для этого не нужен.

Ошибка про сам `platform` — это ошибка конфигурации, а не пользователя: её текст показывать
покупателю не нужно, но проследите, чтобы `platform` уходил со **всех** площадок. Проверить просто: создать тестовый
заказ из бота и из браузера и убедиться, что оба создаются без `400`.

Для каталожных заказов (`POST /api/order/...`) ничего не изменилось — там Paykeeper,
одна касса, и `platform` по-прежнему используется только для оформления уведомлений.

## 3. Расчёт суммы: `GET /api/steam/quote`

Формула стала честной: раньше к сумме пополнения прибавлялась только наша наценка,
теперь учитываются ещё комиссия кассы за приём платежа и за зачисление на баланс Steam.
Из-за этого `total` при той же сумме пополнения **вырос** — это ожидаемо, раньше заказы были в убыток.

Ответ (поля `topupAmount`, `total`, `calc` — на прежних местах):

```json
{
  "topupAmount": 1000,
  "total": 1151,
  "calc": {
    "mode": "steam_topup",
    "topupAmount": 1000,
    "total": 1151,
    "marginPercent": 5,
    "acquiringPercent": 6,
    "payoutPercent": 3,
    "estimatedProfit": 52,
    "commissionPercent": 5
  }
}
```

| Поле | Что это |
|------|---------|
| `total` | Сколько платит покупатель, ₽ — это и показываем |
| `topupAmount` | Сколько зачислится на баланс Steam, ₽ |
| `calc.marginPercent` | Наша наценка, % |
| `calc.acquiringPercent` | Комиссия AuraPay за приём, % |
| `calc.payoutPercent` | Комиссия AuraPay за зачисление в Steam, % |
| `calc.estimatedProfit` | Наша прибыль с заказа, ₽ — **только для админки** |
| `calc.commissionPercent` | Дубль `marginPercent`, оставлен для совместимости |

`estimatedProfit` и проценты кассы **не показывать покупателю**. В пользовательском
интерфейсе — только `total` и `topupAmount`.

Лимиты пополнения не изменились: **25 – 50 000 ₽**.

## 4. Автопополнение Steam

После подтверждения оплаты сервер **сам** отправляет деньги на баланс Steam через AuraPay.
Ручная выдача менеджером больше не нужна — она остаётся только для сбойных случаев.

### Что меняется в жизненном цикле заказа

| Статус заказа | Когда |
|---------------|-------|
| `awaiting_payment` | счёт выставлен, ждём оплату |
| `paid` | касса подтвердила деньги, пополнение запущено |
| `completed` | AuraPay подтвердила зачисление на баланс Steam |
| `payment_failed` | ссылка истекла без оплаты |

Раньше `paid` был для Steam финальным статусом. Теперь оплаченный заказ доходит до `completed`
самостоятельно, обычно за считанные минуты. Если экран заказа считает `paid` конечным
состоянием — стоит показать промежуточное «Пополняем баланс…», а `completed` трактовать как «Готово».

`GET /api/payment/status?id={orderId}` контракт не меняет, `status` просто получает
ещё одно возможное значение — `completed`.

### Ошибка выдачи

Если пополнение не прошло, заказ **остаётся в `paid`**, а админам уходит сообщение со звуком —
дальше человек разбирается вручную. Специального статуса для фронта нет: с точки зрения покупателя
заказ оплачен и в работе. Внутреннее поле `payoutStatus` (`none` / `processing` / `success` / `error`)
наружу не отдаётся, но может понадобиться в админке.

### Проверка логина Steam

`POST /api/steam/create` спрашивает у кассы, сможет ли она пополнить указанный логин.

**Сейчас эта проверка не блокирует заказ** — результат только пишется в лог сервера.
Причина: на 09.08.2026 касса отвечает «не найден» даже на заведомо существующие аккаунты,
и блокировка остановила бы все продажи. Разбираемся с AuraPay.

Когда проверку включат (переключатель на сервере, релиз фронта не нужен), при неизвестном
логине ручка начнёт отдавать `400`:

```json
{ "error": "Не удалось найти аккаунт Steam с таким логином. Проверьте написание логина (не почты и не никнейма)." }
```

Это будет **новый сценарий ошибки на существующей ручке**: раньше `400` приходил только по сумме.
Текст готов к показу пользователю как есть — выводите его прямо под полем ввода логина.
Обработку лучше добавить заранее, чтобы включение на сервере не потребовало правок фронта.

Если сама проверка недоступна (касса не ответила), заказ создаётся как обычно.

## 5. Админка: проценты по Steam

Три процента вынесены в настройки и меняются на лету, без деплоя и рестарта.
Отдельных ручек нет — используются существующие, те же, что для режима техработ.

**Чтение:**

```
GET /api/admin/settings/public
→ { "settings": { "steam_commission_percent": { "value": 5, "type": "number" }, ... } }
```

**Запись:**

```
POST /api/admin/settings/update
{ "key": "steam_commission_percent", "value": 12 }
```

| Ключ | Смысл | Кто меняет |
|------|-------|-----------|
| `steam_commission_percent` | Наша наценка, % | Меняем свободно — это наша маржа |
| `aurapay_acquiring_percent` | Комиссия AuraPay за приём (СБП), % | Только при смене тарифа кассы |
| `aurapay_payout_percent` | Комиссия AuraPay за зачисление в Steam, % | Только при смене тарифа кассы |

Требования к значению:

- слать **числом**, не строкой (`12`, а не `"12"`), иначе `400`;
- допустимо от `0` до `100` **не включая** 100 — на `100` формула расчёта делится на ноль;
- изменение применяется к следующему же запросу `quote`.

Рекомендации по интерфейсу:

- два тарифных поля стоит визуально отделить от нашей наценки и подписать
  «менять только при смене тарифа кассы» — это не маркетинговый рычаг, а факт договора;
- полезно рядом показывать пример: при текущих процентах пополнение на 1000 ₽ стоит покупателю
  `total` ₽, наша прибыль `estimatedProfit` ₽. Значения можно взять прямо из `GET /api/steam/quote?amount=1000`;
- **при наценке 0% прибыль равна нулю, а не убытку** — формула уже покрывает обе комиссии кассы.
  То есть введённый процент это и есть чистая маржа сверх всех издержек.

## 6. Чего фронта не касается

- вебхуки `POST /api/payment/aurapay/callback` и `POST /api/payment/aurapay/payout-callback` — служебные, вызываются кассой;
- поля заказа `paymentProvider`, `paymentShop`, `externalOrderId`, `payoutId`, `payoutCommission` — внутренние;
- какая именно касса обслужит заказ: сервер выбирает сам по `platform`;
- переключатель кассы `STEAM_PAYMENT_PROVIDER` в окружении сервера — на случай отката на Paykeeper;
- чек 54-ФЗ по Steam через AuraPay не передаётся (в их API нет таких полей).
