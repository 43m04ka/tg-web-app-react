# Блок «Каталог»: что есть сейчас и как это сгруппировать

Разбор по факту кода фронта (`src/pages/AdminPanel/Tabs/*`) и бэка
(`tg-web-app-server/routes/*`, `controllers/*`, `models/tables/*`).
Изначально предполагалось, что бэк не меняется вовсе и всё сводится к перегруппировке
экранов. На «Товарах» это не сошлось: без серверного отбора и постраничности фильтры
получались поверх двадцати случайных строк, а массовые действия — циклом запросов.
Поэтому в `adminProductController` добавлены `products`, `products/facets`,
`products/bulk-update`, `products/bulk-delete`. Существующие ручки не менялись.

Файл черновой, под правку: концепция в разделе «Предложение», факты — выше.

---

## 1. Модель данных, как её видит бэк

Понимание иерархии — ключ ко всей перегруппировке. Сейчас интерфейс её не отражает.

```
structurePage (Page)               ← «страница» = раздел бота/витрины
├─ id, name, link, barIcon, serialNumber, isHidden
├─ botType: tg | vk-xbox | vk-ps | web       ← в какой платформе показывается
└─ type:    ps | xbox | ps_india | steam | services | other  ← ЧТО за витрина; определяет
                                                     парсер, сетку цен и вид оформления заказа
                                                     (список типов — pageOptions.js; в БД
                                                      это обычный VARCHAR, не ENUM)
   │
   ├─ catalog[]            (path, structurePageId, isExchangeIndiaCatalog)
   │  └─ product[]         (name, price, oldPrice, onSale, type, catalogId, …)
   │
   ├─ structureCatalog[]   ← блоки самой витрины: group = 'head' (карусель)
   │                          или 'body' (основное содержимое), serialNumber, url,
   │                          path, imageIcon, backgroundColor, скругления
   │
   └─ searchClue[]         ← подсказки в поиске (Page.hasMany(SearchClue))

startPage[]                ← стартовое меню, отдельно по platform (tg/vk-xbox/vk-ps/web),
                              type: label | title | page | link, serialNumber
price_rules_ps / _xb / _ps_india   ← сетки наценки, по одной на тип витрины
```

Два важных следствия:

1. **`page.type` — это и есть «платформа»**: от него зависит, какой парсер дергается
   (`start-parse-ps` vs `start-parse-xbdeals`), какая сетка цен применяется
   (`/price-rules/:platform`) и какие поля показывать. Сейчас пользователь выбирает
   страницу в одной вкладке, а последствия этого выбора видит в трёх других.
2. **`catalog.path` — рабочий идентификатор для парсинга** (`bdPath`), а не просто имя.

## 2. Что делает каждая вкладка сейчас

### 2.1 «Товары» (`edit-cards` → `Tabs/EditCards`) — **переработано**

Раздел «Все товары» из блока 1 сделан. Текущее состояние:

| Что | Как работает |
|---|---|
| Список | `GET /admin/products` — отбор и постраничность (50 на странице) считает сервер |
| Фильтры | поиск по названию (дебаунс 350 мс), каталог, тип, статус; любая смена возвращает на 1-ю страницу |
| Типы для фильтра | `GET /admin/products/facets` — какие типы реально встречаются и сколько их |
| Таблица | `CardTable`: Название (+ID, платформа) / Каталог / Тип / Цена / Статус |
| Массовые действия | `POST /admin/products/bulk-update` и `/bulk-delete` — **один запрос на всю выборку** |
| Редактирование | вкладка `EditDataCard` → `GET /api/product/:id`, сохранение `POST /admin/updateCardData` |
| Итоги действий | тосты `Elements/Feedback`, удаление — через окно подтверждения, не `window.confirm` |

Почему список отдельной ручкой, а не через `searchForName`: тот вытягивает все совпадения
по имени и отдаёт первые 20. Фильтровать эти 20 строк на клиенте бессмысленно — отбор
нужен по всей таблице. Старая ручка осталась нетронутой, ей пользуются другие экраны.

Вкладки карточек **не закрываются** при смене фильтра или страницы (правило дизайн-системы:
«поиск и фильтры открытые вкладки не трогают») — только после реального удаления товара.

Осталось по этому разделу: `price` / `oldPrice` / `priceInOtherCurrency` в форме карточки
всё ещё не объяснены; перенос товара между каталогами по-прежнему невозможен из интерфейса.

**Удалён мёртвый код:** `EditCards/UploadData/`, `EditCards/ExportData/`, `EditCards.new.scss`.

### 2.2 «Каталоги» (`edit-directories` → `Tabs/EditCatalogs/EditDirectories.jsx`, 560 строк)

Фактически это **главный рабочий экран блока**. Список каталогов с фильтром по странице
(вкладки сверху) и поиском по `path`. Статус: `onSale` = 2 «в продаже» / 1 «частично» / 0 «нет».

Действия шапки: «Создать» (только поле `path`, страница берётся из активной вкладки),
«Импортировать» (Excel → `POST /api/product/import?catalogId=`), «Обновить».

Действия строки — **семь кнопок в ряд**:

| Кнопка | Ручка | Смысл |
|---|---|---|
| Карты | `GET /admin/productList?catalogId=&listNumber=` | список товаров каталога (свой, не тот, что во вкладке «Товары») |
| Парсить | `POST /api/parsing/start-parse-{ps,xbdeals}` или `parse-links-{ps,xbdeals}` | большой попап `ParsePopup`, см. ниже |
| Экспорт | `GET /api/catalog/export/:catalogId` | скачать xlsx |
| Пересчитать цены | `POST /api/catalog/recalculate` | применить сетку к уже существующим товарам |
| Перепроверить цены | `POST /api/parsing/recheck` + опрос `GET /recheck/:id` | сходить на витрину и сверить цены, опционально `autoFix` |
| Снять / В продажу | `POST /admin/changeSaleStatusCatalog` | массовый `onSale` по каталогу |
| Удалить | `POST /admin/deleteCatalog` | без подтверждения |

`ParsePopup` — самая насыщенная форма в админке: режим «по каталогу» / «по ссылкам»,
URL категории, кол-во страниц (авто/вручную), для PS — фильтры по типу и платформе,
сортировка, дата окончания акции (авто/вручную), «поверхностный парсинг», «парсить аддоны».
Формально это отдельный инструмент, спрятанный в кнопке строки таблицы.

Мелочи: `console.log(pageList.find(...))` прямо в JSX (строка 545); удаление и снятие
с продажи — без подтверждения; после действий — `setTimeout(…, 150)` вместо ответа сервера.

### 2.3 «Структура» — **раздел убран, механика переехала в «Страницы»**

Отдельного пункта меню больше нет: карусель и основное содержимое редактируются
в правой половине экрана «Страницы», рядом с самой страницей. Раньше страница
выбиралась дважды — в «Страницах» таблицей, в «Структуре» списком кнопок, который
показывался только после «← вернуться к выбору страницы».

Что было и куда делось:

| Было | Стало |
|---|---|
| `EditCatalogs.jsx` + `Head/Head.jsx` (258 стр.) + `Body/Body.jsx` (277 стр.) | одна панель `EditPages/StructurePanel.jsx` |
| `CreateHead.jsx`, `CreateBody.jsx`, `EditDataCatalog.jsx` | одна форма `EditPages/StructureBlockForm.jsx` |
| `AP_CreateNewCatalog` + `AP_SelectInputLabel` (вложенный виджет выбора типа) | декларативное описание `EditPages/structureKinds.js` |
| `Structure.jsx`, `Structure.module.scss` (не в роутах) | удалены |

Head и Body были копиями друг друга и уже разошлись: при создании элемента карусели
можно было задать закругления, а при правке баннера тела нельзя было поменять иконку.
Теперь набор полей задаёт вид блока, а не ветвления в разметке.

**Исправлено по ходу:**

- Кнопка «Вставить» в шапке не делала ничего (пустой `onClick` с комментарием).
  Копирование работает внутри своей группы; вставить слайдер в тело нельзя —
  типы карусели и тела не пересекаются, витрина такой блок не ждёт.
- Перетаскивание строки переписывало `serialNumber` **у всех** блоков группы;
  теперь уходят только реально изменившиеся. Плюс появились стрелки ↑/↓:
  тащить мышью через длинный список неудобно.
- `item['type'].includes(...)` падал на блоке без типа.
- `createStructureCatalog` / `deleteStructureCatalog` / `updateStructureCatalog`
  не проверяли ответ сервера — интерфейс одинаково показывал успех и отказ.
- Удаление блока было без подтверждения.
- Смена вида блока не очищала лишние поля: у переделанного из кликабельного
  в обычный оставался прежний `path`, и витрина продолжала вести на старый адрес.

`deleteDate` (у скидочного каталога) сохранён как есть: поле пишется, но **никем
не читается** — ни витриной, ни бэком. В форме помечено honest-хинтом.

### 2.4 «Страницы» (`pages` → `Tabs/Structure/EditPages/EditPages.jsx`) — **переработано**

| Что | Как работает |
|---|---|
| Список | `pageList` из общего стора в админском режиме (со скрытыми), порядок — по `serialNumber`, как в баре бота |
| Фильтры | поиск по названию/ссылке/ID, витрина (`type`), площадка (`botType`), статус |
| Строка | иконка бара, название, ID и ссылка, тип, площадка, статус |
| Выбор | клик по строке выбирает страницу — ею управляется правая половина; двойной клик открывает настройки |
| Форма | вкладка `PageForm` (`TabPane` + `FormLayout`) вместо попапа: имя, ссылка, порядок, витрина, площадка, «скрыта», иконка |
| Стартовое меню | вынесено отдельным разделом меню (`start-menu`), а не секцией внутри экрана |
| Оформление | правая половина экрана: карусель и тело выбранной страницы (см. 2.3) |
| Итоги действий | тосты и окно подтверждения из `Elements/Feedback` |

Колонки со счётчиками каталогов и блоков из таблицы убраны: экран и так разделён надвое,
и содержимое выбранной страницы видно справа целиком, а не числом.

**Исправлено по ходу:**

- Переключатель «Страница скрыта» писал поле `isHide`, которого у модели нет. Sequelize
  молча отбрасывал его — скрыть страницу из формы было невозможно, хотя список читал
  правильное `isHidden`. Заодно `defaultValue={pageData.isHide}` всегда был `undefined`,
  поэтому переключатель у скрытой страницы выглядел выключенным.
- `botType` (площадка показа) не редактировался нигде, хотя от него зависит, увидит ли
  страницу покупатель. Теперь есть и в списке, и в форме.
- `createPage` / `updatePageData` / `deletePageData` не проверяли ответ сервера: форма
  одинаково показывала успех и когда страница сохранилась, и когда сервер отказал.
- `POST /admin/deletePage` **не проверял доступ вообще** — в отличие от создания
  и обновления. Удаление каскадное (каталоги, блоки, подсказки), то есть самая
  разрушительная ручка раздела была самой открытой. Добавлен `adminAllowed`.
- Убраны `setListButtonData` в теле рендера и мёртвый `listButtonData`,
  удалён попап `EditPageData`.

Осталось: `serialNumber` правится числом руками — перетаскивание строк было бы понятнее.

### 2.5 «Подсказки в поиске» (`search` → `Tabs/Search`)

Простейший CRUD: список подсказок, отфильтрованный по выбранной странице,
создание (`POST /admin/createSearchClue`) и удаление. Редактирования нет.
Полноценная вкладка первого уровня ради одной таблицы из двух колонок.

### 2.6 «Парсинг» (`parsing` → `Tabs/Parsing/Parsing.jsx`)

Вопреки названию **парсинг отсюда не запускается**. Это три таблицы сеток наценки:
PS / XBDeals / India — интервалы `min–max`, тип `MULTIPLIER|FIXED`, значение,
для xb/india ещё `commission`. Сохранение `POST /api/parsing/price-rules/:platform`,
подтверждение через `alert()`.

### 2.7 Что есть на бэке, но не показано в интерфейсе

- `GET /api/parsing/parse-queue` + `POST /parse-queue/:id/cancel` — **общая очередь на источник**
  (PS-Турция и PS-Индия делят одну очередь, т.к. это один домен). Пользователь запускает
  парсинг и не видит, что задача встала в очередь за чужой.
- `GET /api/parsing/recheck` — список всех отчётов перепроверки. Сейчас отчёт виден только
  тому, кто только что нажал кнопку, и теряется при закрытии попапа.
- `POST /api/parsing/expire-promotions` (+ `dryRun`) — ручное завершение истёкших акций.
  Кнопки нет вообще.
- `POST /admin/setExchangeIndiaCatalog` — пометка «каталог для обмена India». В `useServer`
  метод есть, в UI не вызывается.

## 3. Что не так с текущей группировкой

1. **Названия не про то.** «Структура» — это блоки витрины, «Каталоги» — папки товаров,
   «Парсинг» — сетки цен, а сам парсинг — внутри «Каталогов». Угадать невозможно.
2. **Иерархия разорвана.** Страница → каталог → товар — это одна цепочка, но живёт
   в трёх несвязанных вкладках, и в каждой заново выбирается страница
   (свои `useState(page)`, свои табы, своя загрузка `pageList`).
3. **Цены размазаны:** сетка (вкладка «Парсинг») и применение сетки (кнопка в строке
   каталога) — в разных концах админки. Плюс третья кнопка, «Перепроверить», — механика,
   от которой решено отказаться (см. ниже).
4. **Парсинг спрятан.** Самый сложный инструмент — за кнопкой в ячейке таблицы,
   без истории запусков, без очереди, без результата прошлого прогона.
5. **Семь кнопок в строке** — верный признак, что таблица делает работу трёх экранов.
6. **Два разных списка товаров** («Товары» → глобальный поиск, «Карты» → товары каталога)
   с разной вёрсткой и разными возможностями.
7. **Визуал и данные смешаны.** «Первая страница», карусель и body — это оформление бота;
   каталоги и товары — это товарные данные. Сейчас они в одном блоке меню.

## 4. Предложение: три блока вместо одного

Логика деления: **чем оперирует пользователь** — товарными данными, источниками/ценами
или внешним видом бота. Ни одна ручка бэка не меняется, меняется только карта экранов.

### Блок 1. «Товары» — всё, что про сам товарный запас

| Раздел | Что внутри | Откуда собрано |
|---|---|---|
| **Каталоги** | список каталогов с фильтром по странице, статусом и счётчиком товаров; в строке остаются только 3 действия: **Открыть**, **В продажу/Снять**, **⋯** (экспорт, удалить) | «Каталоги» минус парсинг и цены |
| **Карточка каталога** (новый экран, не попап) | шапка: путь, страница, платформа, статус, кнопки «Парсить» и «Пересчитать цены»; вкладки внутри: *Товары* / *История парсинга* / *Импорт-экспорт* | «Карты» + попапы парсинга и цен |
| **Все товары** | нынешний глобальный поиск + фильтры «каталог», «статус», «тип»; массовые операции в один запрос там, где бэк позволяет | вкладка «Товары» |

Импорт и экспорт xlsx **отдельным разделом не выносим** — они всегда про конкретный каталог,
поэтому живут в «Каталогах»: импорт кнопкой в шапке списка (как сейчас), экспорт — действием
строки и вкладкой внутри карточки каталога. Неиспользуемые `EditCards/UploadData` и
`EditCards/ExportData` при этом либо переиспользуются здесь, либо удаляются.

Ключевая идея: **каталог перестаёт быть строкой таблицы и становится страницей**.
Тогда семь кнопок расходятся по вкладкам этой страницы, а не давятся в одну ячейку.

### Блок 2. «Источники и цены» — всё, что тянет данные извне

| Раздел | Что внутри |
|---|---|
| **Парсинг** | запуск (форма из `ParsePopup`, но полноэкранная и с сохранением последних параметров), **текущая очередь** (`GET /parse-queue` — сейчас невидима), история запусков через `processList` |
| **Сетки наценки** | нынешняя вкладка «Парсинг» под честным именем; сетка привязана к типу витрины (ps / xbox / ps_india) — так и подписать |

**Перепроверка цен убирается из админки.** Механика признана лишней: удаляются кнопка
«Перепроверить цены» в строке каталога и компонент `Elements/RecheckPriceTab.jsx`.
Серверную часть не трогаем — ручки `POST/GET /api/parsing/recheck` и `recheckService`
остаются на месте, просто ими никто не пользуется из интерфейса.

Обоснование группировки: PS и Xbox делят очередь по источнику, сетки цен привязаны
к типу витрины. Это одна подсистема, и на бэке она уже собрана в роутере `parsingRoutes` —
интерфейс просто повторит это.

### Блок 3. «Визуал» — всё, что видит покупатель в боте

| Раздел | Что внутри |
|---|---|
| **Страницы** | CRUD `structurePage` + сразу видно: тип витрины, платформа бота, скрыта/нет, сколько каталогов и блоков привязано |
| **Оформление страницы** | нынешняя «Структура»: карусель + основное содержимое, drag&drop; открывается из строки страницы, а не отдельной вкладкой с повторным выбором страницы |
| **Стартовое меню** | `EditStartPages` как самостоятельный раздел (сейчас спрятан второй вкладкой внутри «Страниц») |
| **Акции** | `POST /api/parsing/expire-promotions` с `dryRun` («посчитать» → «применить»), кнопки сейчас нет вообще. Живёт здесь, а не в парсинге: для покупателя это чисто оформление витрины — гаснут плашки скидок |
| **Подсказки в поиске** | таблица из двух колонок — не вкладка первого уровня, а подраздел «Визуала» |

## 5. Сквозные правки, не зависящие от группировки

- **Выбор страницы остаётся локальным** для каждой вкладки (решение принято): общий
  контекст не заводим, каждый экран помнит свою страницу сам.
- **Подтверждения** на «Удалить каталог», «Снять с продажи», «Удалить страницу».
  *Сделан общий компонент — `Elements/Feedback` (`useFeedback().confirm`), подключён
